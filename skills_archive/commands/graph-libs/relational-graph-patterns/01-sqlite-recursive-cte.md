# SQLite recursive CTEs against the seven operations

Every claim below is tagged SPEC (quoted from `sqlite.org/lang_with.html`) or
PROBE (a `:memory:` sqlite3 check run against the exact test vectors in
`~/projects/sprefa/src/graph/walk.rs`, reproducible from
`~/projects/claude-research/labs/relational-graph-survey/probes.py`).
Timing numbers are out of scope; that is the other lab's job
(`labs/graph-sqlite`).

## Self-reference and mutual recursion

SPEC: "the recursive table must appear exactly once in the FROM clause of
each top-level SELECT statement in the recursive-select." One self-reference
per SELECT, and the doc says nothing about a CTE referencing a second CTE
that recurses back into it.

PROBE: two CTEs written to recurse through each other reject at prepare
time:

```
WITH RECURSIVE
  even(n) AS (SELECT 0 UNION ALL SELECT n+1 FROM odd WHERE n < 10),
  odd(n)  AS (SELECT 1 UNION ALL SELECT n+1 FROM even WHERE n < 10)
SELECT * FROM even LIMIT 5
```

```
sqlite3.OperationalError: circular reference: even
```

Mutual recursion is out. Every one of sprefa's seven operations needs at
most one recursive relation per lowered query, so this never binds today,
but it rules out ever lowering, say, a forward-reach rule and a
reverse-reach rule as two CTEs that reference each other's output.

## UNION vs UNION ALL

SPEC, on `UNION`: "only add rows to the queue if no identical row has been
previously added to the queue." On `UNION ALL`: "all rows generated by both
the initial-select and the recursive-select are always added to the queue
even if they are repeats." On why: "UNION is used instead of UNION ALL to
prevent the recursion from entering an infinite loop if the graph contains
cycles."

`UNION` is therefore the one that terminates on a cyclic graph (sprefa's
`edge` relation is exactly this: a code dataflow graph with real cycles from
mutual recursion and callback loops). `UNION ALL` on the same cyclic input
recurses until something else stops it (a depth cap, a row-budget bail, or
memory exhaustion) because it never checks for repeats.

The dedup check is per row against the whole accumulated history ("no
identical row has been previously added"), not a bulk pass at iteration
boundaries. This matters for cost, but exactly how SQLite implements that
check internally (linear scan vs an internal index) is a question for the
timing lab, not this one.

## WHERE clause: does it gate expansion, not just the result

This is the crux question, because it decides whether the halt predicate
(`multi_source_halt_bfs`'s entire reason to exist as hand-written Rust) is
expressible in SQL at all.

SPEC describes the recursion step as: "Pretend that the single row just
extracted is the only row in the recursive table and run the
recursive-select, adding all results to the queue." The recursive-select
(including its WHERE clause) runs once per dequeued row, against that one
row, before its children are ever added to the queue. A WHERE clause that
references the dequeued row's own columns therefore decides whether that
row's children get generated at all, at expansion time, before any of it
reaches a finished result set.

PROBE, matching `walk.rs::halt_node_is_recorded_but_not_expanded` exactly
(chain `0->1->2->3`, seed at node 1, halt at node 2, expected result
`{1,2}` with node 3 absent):

```sql
WITH RECURSIVE walked(node) AS (
  SELECT 1
  UNION
  SELECT e.dst
  FROM walked w
  JOIN edge e ON e.src = w.node
  JOIN halt h ON h.node = w.node
  WHERE h.is_halt = 0
)
SELECT node FROM walked ORDER BY node
```

Result: `[(1,), (2,)]`. Node 2 is recorded (it is in the result) because it
was generated as a child of node 1 before the WHERE clause was evaluated
against node 2 itself; node 3 is absent because the WHERE clause blocked
node 2 from generating children. This is exactly sprefa's halt semantics: a
halted node is a reachable, reported endpoint that does not propagate.
**The halt predicate is expressible in a recursive CTE.** The petgraph lab's
finding that `Bfs`/`depth_first_search` expand-before-return and so cannot
implement this halt check does not carry over to SQL: the WHERE clause runs
per-row before expansion, which is the opposite ordering.

Depth cap is the same mechanism with an arithmetic condition instead of a
flag lookup. PROBE matching
`walk.rs::walk_depth_cap_records_at_cap_but_stops` (chain `0->1->2->3`,
cap 2, expected `{0:0, 1:1, 2:2}`, node 3 absent):

```sql
WITH RECURSIVE walked(node, depth) AS (
  SELECT 0, 0
  UNION
  SELECT e.dst, w.depth+1
  FROM walked w JOIN edge e ON e.src = w.node
  WHERE w.depth < 2
)
SELECT node, depth FROM walked ORDER BY node
```

Result: `[(0,0), (1,1), (2,2)]`. Matches.

## What a recursive CTE does NOT give for free: the min-depth merge

`multi_source_walk` records each node once, at its shortest depth, because
its visited-generation stamp is exactly a `merge(MinBy(depth))` lattice: the
first path to reach a node wins and later, longer paths to the same node
are dropped before they can expand further.

`UNION`'s dedup rule compares the whole row, not one key column. Two paths
to the same node at two different depths are two different rows, so both
survive. PROBE, matching `walk.rs::walk_keeps_min_depth_when_two_paths`
(`0->1->4` at depth 2 and `0->2->3->4` at depth 3):

```sql
WITH RECURSIVE walked(node, depth) AS (
  SELECT 0, 0
  UNION
  SELECT e.dst, w.depth+1
  FROM walked w JOIN edge e ON e.src = w.node
)
SELECT node, depth FROM walked ORDER BY node, depth
```

Result includes both `(4, 2)` and `(4, 3)`. Getting only the minimum back
out requires a separate `GROUP BY node` pass after the recursive CTE
finishes, and on a graph with many alternate paths to the same node the
working table can carry every one of those paths until that collapse runs,
not just the winning one. sprefa's own BFS never materializes a losing path
in the first place. DuckDB's `USING KEY` clause (below, and in
[03-sql-pgq-and-duckdb.md](03-sql-pgq-and-duckdb.md)) is the one SQL dialect
found in this survey that closes this gap directly, by making the union
table a dictionary keyed on the node column instead of an append-only log.

## LIMIT, ORDER BY, depth columns

SPEC on `LIMIT`: "The LIMIT clause, if present, determines the maximum
number of rows that will ever be added to the recursive table in step 2b.
Once the limit is reached, the recursion stops." A hard global cap on total
rows ever generated, not a per-branch cap.

SPEC on `ORDER BY`: "If an ORDER BY clause is present, it determines the
order in which rows are extracted from the queue in step 2a." This
controls traversal order (BFS-like vs DFS-like) by controlling dequeue
order, exactly the way a priority queue would in a hand-written walk.

SPEC on depth columns: no dedicated syntax; the documented idiom is a
plain integer column incremented in the recursive term
(`under_alice.level+1`), which is what both probes above use.

## Documented restrictions

SPEC: "Recursive SELECT statements may not use aggregate functions or
window functions." This rules out doing the min-depth collapse (previous
section) inside the recursive term itself; it has to happen in a
non-recursive query wrapped around the finished CTE, after termination.

SPEC: "the recursive table must appear exactly once in the FROM clause"
(already covered above, restated here as the general restriction, not just
the mutual-recursion case).

SPEC: "The initial-select may be a compound select, but it may not include
an ORDER BY, LIMIT, or OFFSET." Only the outer query gets those clauses;
the seed step cannot be pre-sorted or pre-limited on its own.

## Reading against the seven operations

| operation | blocked by a documented restriction | notes |
|---|---|---|
| `tarjan` / SCC | no | SCC in a recursive CTE means iterating reachability both directions per candidate component; expressible but is a different algorithm shape entirely, not covered by these restrictions |
| `build_condensed` | no | same caveat |
| `count_pairs` | no | expressible as `COUNT(*)` over a recursive CTE seeded from every node (cross join every node against itself), which is exactly the Theta(V^2) pair table `scc.rs`'s own comment says the condensation approach exists to avoid |
| `reaches_from` | no | ordinary recursive CTE, one seed row |
| `reached_by` | no | ordinary recursive CTE over the reversed edge direction |
| `multi_source_walk` (depth cap) | no | verified above |
| `multi_source_halt_bfs` | no | verified above, contrary to the intuition the petgraph lab's finding might suggest |

None of the seven operations hits a hard documented wall in SQLite's
recursive CTE grammar. The two costs the spec text surfaces on its own,
independent of any timing measurement, are: the `UNION` per-row dedup
against full accumulated history (aggravated for the min-depth case, which
needs a second pass since aggregates cannot run inside the recursive term),
and the absence of a value-per-key merge primitive, so anything shaped like
`multi_source_walk`'s min-depth guarantee costs an extra materialize-and-
collapse round trip that the hand-rolled Rust BFS never pays.
