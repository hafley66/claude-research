# Datafun: Datalog as a typed functional language

Source pair: Arntzenius & Krishnaswami, *Datafun: a Functional Datalog*, ICFP
2016[^datafun16]; and *Seminaïve Evaluation for a Higher-Order Functional
Language*, POPL 2020 (PACMPL 4:POPL, Article 22)[^seminaive20]. The 2020 paper
reformulates the 2016 calculus around an explicit modality; both are cited
below where their syntax diverges.

## 1. Thesis

Datafun takes Datalog's one real constraint — recursive rules must monotonically
grow a fixed point, or the fixed point isn't unique and doesn't terminate — and
promotes it from a syntactic restriction (stratification, range-restriction,
constructor-freeness) to a **type**. Every Datafun type carries a partial order;
every well-typed function is monotone with respect to it, by construction, the
same way a well-typed pure function in ML can't perform IO. Non-monotone
operations (equality tests, negation, aggregation) don't get banned — they get
walled off behind a modality (`□A`, "discrete/boxed A") that a monotone context
can never see into. The payoff: Datalog's fixed-point core embeds losslessly
into a full higher-order functional language, because monotonicity — the one
property `fix` needs — is now a typechecker fact instead of a language-wide ban
on `λ`, sums, or first-class relations.

## 2. Core types and constructs

### Finite sets + comprehensions

```
types    A, B ::= 1 | A × B | A + B | A → B | □A | {A}          -- Fig 1, [^seminaive20]
```

`{A}` is finite-set-of-`A`, ordered by inclusion (`x ⩽ y :{A} ⇐⇒ x ⊆ y`).
Comprehension desugars to monadic `for`/`when`[^seminaive20 Fig.2]:

```
{e | x ∈ s, guard}   ~~>   for (x ∈ s) when (guard) {e}
```

`for (x ∈ e) f` is the union, over every `x ∈ e`, of `f` — the set monad's
bind. This *is* the join operator a Datalog rule body compiles to; a rule with
several body atoms is nested `for`s with a `when` guard for each equality.

### The two function arrows (2016 design)

The 2016 paper tracks monotonicity with **two arrow types** and two matching
variable kinds — discrete `x` (any use) and monotone `x` (usable only where
the surrounding expression must stay monotone):

```
A, B ::= ... | A → B | A →+ B                                    -- Fig 1, [^datafun16]
```

```
map    : (A → B)  → {A} →+ {B}        map f A    = {f x | x ∈ A}    -- ordinary arrow: f need not be monotone
filter : (A →+ 2) → {A} →+ {A}        filter f A = {x | x ∈ A, f x} -- monotone arrow: f MUST be monotone
```

`map (≤0) {0,1} ⊄ map (≤1) {0,1}` — mapping a non-monotone predicate over a
set isn't monotone in the predicate, so `map` takes it via the *discrete*
arrow. `filter (≤0) {0,1} ⊆ filter (≤1) {0,1}` always holds, because
`filter`'s guard sits inside a comprehension, which Datafun's typechecker
proves monotone in the guard automatically[^datafun16 §3.1].

### The discreteness modality `□A`

The 2020 paper deletes the two-arrow split and replaces it with **one** arrow
(always monotone) plus a comonadic type `□A`[^seminaive20 §2.2, Fig.1]:

```
□A            -- same elements as A, ordered DISCRETELY: x ⩽ y :□A ⇐⇒ x = y
[e]           -- introduction: box e (e may only mention discrete variables)
let [x] = e in f   -- elimination: unbox e, binding discrete x in f
```

Why it exists: a function `□A → B` is *vacuously* monotone (`x = y` implies
`f x ⩽ f y` by reflexivity, since `⩽` on `□A` collapses to `=`). So ordinary,
possibly non-monotone functions `A → B` are recovered *inside* an all-monotone
type theory as `□A → B` — non-monotonicity isn't disallowed, it's confined to
arguments the typechecker has frozen. Equality tests, negation, and aggregate
seeds all take their operand boxed:

```
¬     : □bool → bool
member : □A → {A} → bool          -- x boxed: increasing x can flip membership
```

### `fix`: least fixpoint, typed at a semilattice

```
fix x is e                 -- sugar, [^seminaive20] Fig.2
    ~~>  fix [λx. e]
```

Side condition ([^seminaive20] §2.2; the `fix` rule takes `e : □(fixL → fixL)`):

1. Recursion type is a **semilattice with no infinite ascending chains**
   (`fixL`): a join `∨`, a bottom `⊥`, so iteration from `⊥` terminates.
2. The recursive function is **boxed**: `□(fixL → fixL)`. Boxed terms may only
   mention discrete variables, so a `fix` can't close over an enclosing
   `fix`'s monotone variable — no nested fixed points (mutual recursion via
   product types is still fine).

`fix` is Datafun's only source of unbounded iteration; nothing else loops.

## 3. Three programs, real syntax

**(a) Transitive closure via comprehension + `fix`** — composition defined by
comprehension, transitive closure as its least fixed point[^seminaive20 §3.1]:

```
• : {A × B} → {B × C} → {A × C}
s • t = {(a, c) | (a, b1) ∈ s, (b2, c) ∈ t, b1 = b2}

trans : □{A × A} → {A × A}
trans [edge] = fix s is edge ∨ (edge • s)
```

Typechecks because `∨` (join) and `•` (built from a comprehension, itself
monotone in both arguments) are both monotone in `s`, so `λs. edge ∨ (edge • s)`
is a monotone endofunction on the semilattice `{A × A}` — exactly `fix`'s side
condition. `edge` is boxed because it's used *inside* the fixed point body,
where only discrete variables are visible.

**(b) A monotone query joining two relations** — Datalog `path` restated as a
Datafun function, the shape every recursive stratum in a Datalog engine
compiles to[^seminaive20 §4]:

```
step : {A × A} → {A × A} → {A × A}
step edge path = edge ∪ {(x, z) | (x, y) ∈ edge, (y, z) ∈ path}
```

Two-relation join (`edge`, `path`) inside a comprehension, unioned with the
base case. Typechecks as monotone in `path` (comprehension over a joined
variable is monotone by the same rule as `filter`'s guard); `fix step` is
`trans` inlined.

**(c) `□` admitting a non-monotone test — set difference** — negation, boxed
so it can't be used inside a `fix` body without going through `fix` a second
time, which enforces stratification by construction[^seminaive20 §3.1]:

```
¬ : □bool → bool
¬[t] = case empty? t of in1 () → true; in2 () → false

\ : {A} → □{A} → {A}
s \ [t] = {x | ¬[member [x] t]}
```

`t` is boxed in both: `empty? t` and `member [x] t` are equality/membership
tests, non-monotone in `t` (`t` growing can flip a match from present to
absent). Boxing `t` means `\` can only be applied to a `t` that's already
*finished changing* — the same discipline stratified Datalog imposes by
requiring a negated predicate be fully derived before its negation reads it.

## 4. Seminaive as a derivative

The 2020 paper's central move: classic seminaive evaluation — rewrite each
recursive rule so its body reads only the *new* rows from last round, not the
full relation — turns out to be one instance of a general fact about monotone
functions. Every monotone `f : L → L` on a semilattice has a **derivative**
`f′ : □L → L → L` such that `dx :: x ⇝ y ⟹ f′ x dx :: f x ⇝ f y` (`dx` "changes
`x` into `y`"); given `f` and `f′`, the fixed point is computable by
`x₀ = ⊥, dx₀ = f ⊥, xᵢ₊₁ = xᵢ ∨ dxᵢ, dxᵢ₊₁ = f′ xᵢ dxᵢ`
(`semifix`, [^seminaive20] §4.3, Lemma 4.1), converging exactly when `L` has
no infinite ascending chain. Classic Datalog seminaive is the first-order case
of this — `step′` below *is* `step`'s derivative, computed by hand instead of
by a general `Derive` transform, because a first-order Datalog rule only ever
has one shape (a conjunctive join) to differentiate:

```
step  path = edge ∪ {(x, z) | (x, y) ∈ edge, (y, z) ∈ path}
step′ dpath = {(x, z) | (x, y) ∈ edge, (y, z) ∈ dpath}          -- [^seminaive20] §4.1

step (path ∪ dpath) = step path ∪ step′ dpath                    -- the algebraic law that makes it correct
```

`sprefa`'s `evalRecursiveStratum` in `v6/sprefa-store/js/src/lower/lowerSql.ts`
(lines 120–177) is the SQL rendering of this loop, minus the general
`Derive`/`ϕ`/`δ` machinery: one `_dl_delta_<rel>` table per recursive rel,
seeded from the exit rules, then each round re-runs every rule once per
recursive body position with *that one position* bound to its delta table and
the rest to the full table (`insertNewRows`, `bodyPositionOverrides`), keeping
only rows not already in the full table (`... EXCEPT SELECT ... FROM <full>`,
lines 191–195) as the next delta. Rule bodies are plain conjunctive joins, so
the per-body-position rewrite done by hand *is* `step′` — no need for the
general incremental-λ-calculus transform, because the rule shapes it would
differentiate reduce to the one case (`step`/`step′`) motivating it.

## 5. Why this repo cares

- **Monotonicity-in-types is the read/write split at a finer grain.** Datafun
  tags every *variable* monotone-or-discrete; sprefa's engine tags every *rel*
  source-or-derived (`RelDecl.origin`) and refuses to mix a source rule and a
  derived rule on one rel (`rebuild_derived`'s `DELETE FROM` would wipe
  reconciled source rows) — the same non-monotone/monotone boundary, enforced
  at rel granularity instead of expression granularity.
- **`□` is the formal shape of "materialize before you read it."** Stratified
  negation compiles to `NOT EXISTS` (`lowerSql.ts` lines 253–271) only because
  strata are topologically ordered so the negated rel is a finished table by
  the time its reader runs — structurally `letbox`'s "cash in a boxed
  expression," done at the table level instead of the term level.
- **`fix`'s side condition is why `stratify()`/`scc()` exist.** Datafun's
  typechecker rejects a `fix` whose body isn't a monotone endofunction on a
  semilattice; sprefa has no such typechecker, so `NonStratifiableError` from
  `rulegraph.ts` is the same check performed operationally, post hoc, over the
  rule graph's strongly connected components.
- **`AggregateInRecursionError`** (`lowerSql.ts` lines 52–57, thrown when an
  aggregate head sits inside a recursive SCC) is a monotonicity violation in
  the Datafun sense — `count`/`sum` aren't monotone under `⊆` — caught by a
  hand-written guard instead of type inference, at the same point in the
  pipeline `fix`'s side condition would reject it.
- **`semifix`'s derivative generalizes what `evalRecursiveStratum` special-
  cases.** sprefa gets away with hand-differentiating each rule shape because
  every rule body is a first-order join; a higher-order rule body (a rule
  parameterized over a function, Datafun-style) would need the general
  `Derive` transform sprefa doesn't have and currently has no rule shape that
  would require.
- **rxjs is outside anything Datafun models.** `fix` is pure and total; the
  effect boundary sprefa is theory-crafting on rxjs has no Datafun analogue —
  worth naming as a real gap rather than reaching for a false correspondence.
