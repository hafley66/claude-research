# Datafun math prerequisites: decoding Arntzenius & Krishnaswami, ICFP 2016

Datafun's pitch: track monotonicity in the type system so a `fix` (least-fixpoint) term is
guaranteed to terminate. Everything below is the minimum math to read that sentence as a
typed inference rule instead of as marketing copy. Verified against the paper's own PDF[^datafun],
not paraphrased from memory: quotes below are the paper's actual notation.

The audience is a working programmer with a weak math background. Each concept below gets three
things in order: a plain-English intuition grounded in code, a concrete worked example on actual
small sets, and an ASCII picture. Read the pictures. They are the content.

## 1. The math, taught

### 1.1 Poset (partially ordered set)

**Intuition.** A poset is a set plus a `≤` relation where some pairs are comparable and some are
not. You already know one: subtyping. `Cat ≤ Animal`, `Dog ≤ Animal`, but `Cat` and `Dog` are
incomparable. Three laws: reflexive (`x ≤ x`), transitive (`x ≤ y` and `y ≤ z` give `x ≤ z`),
antisymmetric (`x ≤ y` and `y ≤ x` force `x = y`, so no ties between distinct elements).

**Example.** The divisors of 12, `{1, 2, 3, 4, 6, 12}`, ordered by "divides": `a ≤ b` means
`a` divides `b`. Reflexive: `4` divides `4`. Transitive: `2` divides `4` and `4` divides `12`,
so `2` divides `12`. Antisymmetric: if `a` divides `b` and `b` divides `a`, then `a = b`.
`4` and `6` are incomparable (neither divides the other).

**Visual.** A Hasse diagram draws only the covering edges (an edge from `a` up to `b` with nothing
strictly between means `a ≤ b`); transitivity and reflexivity are left implicit.

```
          12
         /  \
        4    6
        \   / \
         \ /   \
          2     3
           \   /
            \ /
             1

  edges: 1|2, 1|3, 2|4, 2|6, 3|6, 4|12, 6|12
  read upward = "divides". 1 is at the bottom (divides everything).
```

**Non-example.** Add a cycle and antisymmetry breaks. Take three tasks with "must finish before":

```
   a ──→ b ──→ c ──→ a
   a ≤ b, b ≤ c, c ≤ a, yet a, b, c are distinct.
```

Transitivity gives `a ≤ c` and the cycle gives `c ≤ a`, so antisymmetry demands `a = c` while the
three stay distinct. Antisymmetry fails; it is only a preorder. This is exactly the "circular
dependency" a build graph rejects.[^davey]

### 1.2 Join-semilattice, bottom, join

**Intuition.** A join-semilattice is a poset where any two elements have a single *least upper
bound*, written `a ∨ b` (their "join"), and there is a least element of the whole set, written
`⊥` or, in Datafun, `ε`. In code: `∨` is "merge two results," `ε` is "the empty starting
accumulator." Set union is a join; `∅` is its bottom.

**Example.** The powerset of `{a, b}`: `{ ∅, {a}, {b}, {a,b} }`, ordered by `⊆`. Bottom is `∅`.
Joins are unions: `{a} ∨ {b} = {a,b}` (least set containing both), and `{a} ∨ {a,b} = {a,b}`.

**Visual.**

```
        {a,b}      ← top (join of everything)
        /   \
      {a}   {b}
        \   /
         ∅         ← ⊥ = ε (bottom)

  {a} ∨ {b}  = {a,b}   (walk up to the lowest common point)
  {a} ∨ {a,b} = {a,b}
```

**Non-example.** A poset where two elements have upper bounds but no *least* one is not a lattice.
Two minimal tasks `1, 2`, two maximal tasks `3, 4`, each maximal above each minimal:

```
      3     4
      |\   /|
      | \ / |
      |  X  |
      | / \ |
      |/   \|
      1     2

  1 ∨ 2 = ?  upper bounds are {3, 4}, and 3, 4 are incomparable,
  so there is no LEAST upper bound. Join undefined ⇒ not a semilattice.
```

Datafun's set type `{A}` is always a semilattice (union and `∅`), so this failure never bites its
`fix`.[^davey]

### 1.3 Monotone (order-preserving) map

**Intuition.** `f` is monotone when growing the input only grows the output: `a ≤ b` implies
`f(a) ≤ f(b)`. In a picture of two posets with arrows from input to output, monotone means no
arrow drags a lower point above a higher one. This one property is what Datafun's entire type
system exists to track, because a monotone body is what makes `fix` safe.

**Example (monotone).** On the powerset of `{a,b}`, let `f(S) = S ∪ {a}` ("ensure `a` is in").

```
  domain P{a,b}      f = (S ↦ S ∪ {a})       codomain P{a,b}
  {a,b}  ──────────────────────────────────→ {a,b}
  {b}    ──────────────────────────────────→ {a,b}
  {a}    ──────────────────────────────────→ {a}
  ∅      ──────────────────────────────────→ {a}

  Check: ∅ ⊆ {b} in the domain; images {a} ⊆ {a,b} in the codomain. Order kept. ✓
```

**Example (non-monotone).** Boolean negation `¬` on the two-element chain `false ≤ true`.

```
  domain 2          f = ¬            codomain 2
  true   ─────────────────────────→ false
  false  ─────────────────────────→ true

  Domain order:  false ≤ true.
  Images:        ¬false = true,  ¬true = false,  so ¬(false) ≥ ¬(true).
  The ≤ got flipped. ¬ is NOT monotone.
```

The flipped arrow is the whole reason Datafun cannot give `¬` a monotone arrow type; it must be
boxed (see §3).[^davey]

### 1.4 Complete lattice and the least fixpoint by iteration

**Intuition.** A complete lattice has a least upper bound for *every* subset (§1.2 gave that only
for pairs).
Knaster-Tarski says every monotone `f` on one has a least fixed point (a value with `f(x) = x`,
the smallest such). The constructive way to find it is the loop you already write: start at `⊥`,
apply `f`, apply again, and stop when the value stops moving. This is the single most important
picture in the document, because it *is* "loop until nothing changes."

**Example.** The four-element chain `0 ≤ 1 ≤ 2 ≤ 3` (a lattice: join is `max`). Let
`f(x) = min(x + 1, 3)`, which is monotone. Iterate from `⊥ = 0`.

**Visual.**

```
  f(x) = min(x + 1, 3)   on the chain   0 ≤ 1 ≤ 2 ≤ 3

    ⊥      = 0
    f(⊥)   = 1
    f²(⊥)  = 2
    f³(⊥)  = 3
    f⁴(⊥)  = 3      ← f(3) = 3, value unchanged = least fixed point

  ascending ladder (each rung ≥ the one below):

    0 ──→ 1 ──→ 2 ──→ 3 ──→ 3
       f     f     f     f  (stable, halt here)
```

Because `⊥` is below everything, `⊥ ≤ f(⊥)`; monotonicity then propagates that upward at every
step, so the ladder never descends.[^davey]

### 1.5 Ascending chains, finite height, termination

**Intuition.** An ascending chain is `x₀ ≤ x₁ ≤ x₂ ≤ …`. A poset has *finite height* when its
longest such chain has a bounded length. Finite height is precisely the guarantee that the §1.4
loop halts: each strict step climbs one rung, and there are only finitely many rungs, so the loop
runs out of room and stabilizes.

**Example and visual.** One chain must stop; one never does.

```
  Finite height (powerset of {a,b}, height 2):

     ∅  ⊂  {a}  ⊂  {a,b}          longest strict chain = 3 elements, then STOP.
                                   No 4th distinct set to climb to.

  Infinite (ℕ under ≤, no top):

     0 ≤ 1 ≤ 2 ≤ 3 ≤ 4 ≤ ...      always a strictly larger element, NEVER stabilizes.
```

Datafun's finite semilattice types (`L_fin`) are the left case, which is why its `fix` is a loop
that provably terminates and needs no separate proof from the programmer.[^davey]

### 1.6 Finite powerset as a monad

**Intuition.** `Pfin(A)` is "finite sets of `A` values." A monad is a type with two operations:
`unit` (wrap one value) and `join` (flatten one level of nesting). For finite sets, `unit` is
"singleton" and `join` is "union everything together." This is the plumbing behind set
comprehensions.

**Example and visual.**

```
  unit  (wrap a value in a singleton):
     1  ↦  {1}
     7  ↦  {7}

  join  (flatten a set of sets by unioning):
     { {1}, {1,2} }  ↦  {1} ∪ {1,2}  =  {1,2}
     { {a}, {b}   }  ↦  {a} ∪ {b}    =  {a,b}
```

Datafun's `{A}` type is exactly `Pfin(A)`: the singleton `{e}` is `unit`, and the big union that a
comprehension performs is `join`.[^nlab-pfin]

### 1.7 Functors and natural transformations

**Intuition.** A functor is a container you can `map` over: it carries a function `A → B` to a
function on the container while keeping the shape. A natural transformation is a shape-changing
operation that works "the same way" regardless of the element type, so it commutes with `map`.
`reverse` on lists is one: reversing then mapping equals mapping then reversing.

**Example.** Functor `List`, `map double [1,2,3] = [2,4,6]`. Natural transformation
`reverse : List ⇒ List`, with component `reverse` at each element type.

**Visual.** The naturality square, filled with real values (`f = double`, start at `[1,2,3]`):

```
              map double
    [1,2,3] ───────────────→ [2,4,6]
       │                         │
 reverse│                        │reverse
       ↓                         ↓
    [3,2,1] ───────────────→ [6,4,2]
              map double

  Both routes from [1,2,3] land on [6,4,2]:
    down-then-across:  reverse → [3,2,1],  map double → [6,4,2]
    across-then-down:  map double → [2,4,6],  reverse → [6,4,2]
  The square commutes, so reverse is natural.
```

`length : List ⇒ (const ℕ)` is another (mapping a function cannot change how many elements there
are). Datafun's denotations (Fig. 9-10) are built from functors like these.[^milewski]

### 1.8 Comonad and the discreteness comonad `Disc`

**Intuition.** A comonad is the dual of a monad: instead of wrapping and flattening, it exposes
`extract` (read the value out) and `duplicate` (nest a layer). Datafun's comonad is `Disc`:
take a poset and *throw away its order*, leaving a bare set of the same points. A value under
`Disc` is frozen, so any consumer is free to treat it non-monotonically.

**Example and visual.** Apply `Disc` to the two-element chain `false ≤ true`. Same two points,
order edge deleted.

```
   poset 2:                Disc(2):

     true                    true      (no edge)
      |          ═══════►
     false                   false

   false ≤ true              false and true now incomparable:
                             false ⋠ true  and  true ⋠ false
```

The operations, concretely:

```
  extract   : Disc A → A          extract(Disc true)  = true
  duplicate : Disc A → Disc(Disc A)   duplicate(Disc true) = Disc(Disc true)
```

Deleting the edge is what lets `¬` (from §1.3) consume its argument: with no order to respect,
"order-reversing" is no longer a violation. Boxed = frozen = used non-monotonically.[^nlab-comonad]

### 1.9 Adjunction (at the box-modality level)

**Intuition.** An adjunction `F ⊣ U` pairs a "free construction" `F` with a "forget" `U` so that
maps out of the free thing correspond exactly to maps into the forgetful image:
`Hom(F X, Y) ≅ Hom(X, U Y)`. The free join-semilattice on a set is its powerset, and a
semilattice map out of it is pinned down entirely by where it sends the original generators.

**Example and visual.** Free join-semilattice on `{a, b}` is `P{a,b}` under `∪`.

```
  free semilattice on {a,b}  =  P{a,b} with ∪ :

        {a,b}
        /   \
      {a}   {b}
        \   /
         ∅  = ⊥

  Hom-bijection, one concrete instance, target M = ({F,T}, ∨):

    Set-map     g : {a,b} → {F,T}          a ↦ T,  b ↦ F
      ≅
    SemiLat-map ĝ : P{a,b} → ({F,T}, ∨)    the UNIQUE ∨-preserving extension of g
        ∅     ↦ F           (⊥ ↦ ⊥)
        {a}   ↦ T
        {b}   ↦ F
        {a,b} ↦ T ∨ F = T

  Pick where a and b go (the Set-map g); the whole semilattice map ĝ is then forced.
```

Datafun chains two such adjunctions, `Set ⇄ Poset ⇄ SemiLat` (Fig. 7). The `Disc` comonad of
§1.8 lives at the `Set ⇄ Poset` joint; the free-semilattice adjunction above is the
`Poset ⇄ SemiLat` joint that models the `{A}` type.[^milewski]

**Skip entirely on a first pass:** general recursion / domain theory (Scott-continuity, ω-CPOs;
Datafun's fixpoints only need finite height, a strictly weaker and more elementary fact);
limits, colimits, Kan extensions (never invoked); the full proof theory of linear logic (only
the "!" comonad *analogy*, one sentence, matters); the PER logical-relations termination proof
in the paper's §5.4/§6.2 (needed only to verify the metatheory, not to read the design); the
bidirectional type-inference and polymorphism discussion in §8/§9 (implementation notes, not
the type system).

## 2. Reading a typing judgment

`Γ ⊢ e : A` reads right-to-left, then left: "term `e` has type `A`, derivable using the
assumptions listed in context `Γ`." `Γ` is a list `x₁:A₁, …, xₙ:Aₙ` of free variables and their
types. `⊢` ("turnstile") means "proves" / "derives."

A natural-deduction rule is premises stacked over a line, conclusion below it, rule name to the
side:

```
  premise-1     premise-2
  ─────────────────────────  RULE-NAME
        conclusion
```

Read it as: "if you already have derivations of the premises, you may derive the conclusion."
Rules chain into trees: a full typing derivation is premises all the way down to axioms (rules
with zero premises, like a bare variable lookup).

**Worked micro-example**, the identity function on booleans, `λx. x : 2 → 2`, built from
Datafun's own `VAR` and `λ` rules[^datafun]:

```
   x:2 ∈ (x:2)
  ────────────── VAR
   x:2 ⊢ x : 2
  ───────────────────── λ
   · ⊢ λx. x : 2 → 2
```

`VAR` is an axiom: no premises, just a side-condition (`x:2` is literally in the context), which
is why the line above it is empty. `λ` takes one premise (the body typechecks with `x`
added to the context) and concludes the whole abstraction is well-typed in the *outer* context
(here, empty, so no free variables).

## 3. The box modality decoded

Standard framing first, then the correction: a modality `□A` marks a value of `A` that is
**usable non-monotonically**: frozen, constant, "the same regardless of which point in the
order you're looking from." A monotone-typed language needs it because *most* useful functions
(negation, equality tests, string comparison) fail monotonicity, and a type system that only
admits monotone functions would be unable to express them at all without an escape hatch.

**Datafun's own escape hatch is not spelled `□`.** The paper does not put a box type former in
its surface syntax (Fig. 1 has no `□A`). Instead it splits the typing context in two: `∆`
(discrete variables, drawn in italics) and `Γ` (monotone variables, drawn bold), judgment
`∆; Γ ⊢ e : A`. A variable bound in `∆` *is* a boxed value, with nothing about it assumed
order-respecting. Several rules "wipe" `Γ` to empty when typechecking a subterm that must be
constant; the paper names this explicitly:

> "This technique of wiping clean the monotone context to guarantee constancy of a subterm
> recurs in several other rules. Readers familiar with linear logic's `!` comonad … or with
> judgmental formulations of modal logics of necessity (Pfenning and Davies 2001) may notice a
> feeling of déjà vu; indeed, there is a hidden comonad at work here." (§4.1[^datafun])

So: `∆; Γ ⊢ e : A` already **is** a modal judgment, in Pfenning-Davies dual-context style. The
"box introduction" rule is any rule that types a subterm as `∆; · ⊢ e : A` (empty `Γ`) inside a
premise; `APP`'s treatment of its argument is the canonical instance, decoded in §5.

**Smallest contrasting example**, straight from the paper's primitives (Fig. 4):

```
¬     : 2 → 2      -- discrete arrow. false<true but ¬false=true, ¬true=false:
                      order-REVERSING, so ¬'s argument must be boxed/constant.

filter : (A →+ 2) → {A} →+ {A}   -- monotone arrow on the predicate:
   filter (≤0) {0,1} ⊆ filter (≤1) {0,1}   -- growing the predicate only grows the result
```

`¬` cannot be given the monotone arrow type `2 →+ 2`: it would violate monotonicity outright.
`filter`'s predicate argument *can* be monotone, and Datafun's type system proves it is, because
application of a monotone function to a monotone argument stays monotone, and testing a boolean
guard inside a set comprehension is monotone in that guard.[^datafun] `map`'s function argument,
by contrast, is typed discrete (plain `→`) precisely because `map (≤0) {0,1} ⊄ map (≤1) {0,1}`:
it fails monotonicity, so it must be boxed.

## 4. `fix` decoded

General background (Knaster-Tarski): on a complete lattice, any monotone `f` has a least fixed
point, obtained as the meet of every `x` with `f(x) ≤ x`. This exists non-constructively, with
no iteration required and no finiteness required.

**Datafun proves something narrower and constructive instead.** The paper never cites
Knaster-Tarski by name; it proves its own Lemma 4:

> "Any monotone map `f : P → P` on a poset `P` of finite height with a least element `ε` has a
> least fixed point of the form `fⁿ(ε)`." (§5.3[^datafun])

Proof sketch (the paper's own): `ε ≤ f(ε)` (bottom is least), so by monotonicity
`fⁱ(ε) ≤ fⁱ⁺¹(ε)` for all `i`, an ascending chain. Finite height forbids an infinite strictly
ascending chain, so the chain must stabilize: some `fⁿ(ε) = fⁿ⁺¹(ε)`, a fixed point, and it is
provably the *least* one. This is Knaster-Tarski's existence argument specialized to finite
height, traded for a constructive halting *procedure*: "iterate from bottom until nothing
changes," the §1.4 ladder made into an algorithm.

Datafun's typing rules for `fix` (Fig. 5)[^datafun], where `L_fin` = finite semilattice eqtype:

```
   ∆; Γ, x:L_fin ⊢ e : L_fin
  ────────────────────────────  FIX
     ∆; Γ ⊢ fix x is e : L_fin


   ∆; Γ ⊢ e₁ : L_eq     ∆; Γ, x:L_eq ⊢ e₂ : L_eq
  ─────────────────────────────────────────────── FIX≤
        ∆; Γ ⊢ fix x ≤ e₁ is e₂ : L_eq
```

`FIX` requires the loop body `e` to be monotone in `x` (typed with `x` in the monotone context
`Γ`) and the type `L_fin` to be a semilattice (has `ε`, `∨`) *and* finite (guarantees the finite
height Lemma 4 needs). `FIX≤` relaxes "finite type" to "provide an explicit upper bound `e₁`,"
clamping the iteration so it still halts even over an infinite type like `str`.

**Micro-example**, transitive closure, "keep applying until nothing changes," typed:

```
parent, ancestor : {person × person}
ancestor = fix X is parent ∨ (X • X)
```

`X • X` is relation composition. Each iteration adds every pair reachable by one more hop; `∨`
(set union) merges it with what's already known; the type `{person × person}` is a finite
semilattice (person is a finite eqtype), so `FIX` applies directly and Lemma 4 guarantees the
loop halts at the actual transitive closure, with no separate termination proof required from the
programmer.[^datafun]

**Round-by-round trace**, the concrete ascending chain of Lemma 4. Take the three-person graph
`parent = {(a,b), (b,c)}`:

```
  the graph:   a ──→ b ──→ c

  X₀ = {}                              start at ⊥ = ∅
  X₁ = parent ∨ (X₀ • X₀)
     = {(a,b),(b,c)} ∨ (∅ • ∅)
     = {(a,b),(b,c)}                   the parent edges appear
  X₂ = parent ∨ (X₁ • X₁)
     = {(a,b),(b,c)} ∨ {(a,c)}         (a,b)•(b,c) = (a,c): the +1-hop pair
     = {(a,b),(b,c),(a,c)}
  X₃ = parent ∨ (X₂ • X₂)
     = {(a,b),(b,c),(a,c)}             X₂•X₂ = {(a,c)} again, adds nothing
     = X₂                              unchanged ⇒ STOP

  ascending chain:  X₀ ⊆ X₁ ⊆ X₂ = X₃
                    ∅  ⊆ 2   ⊆ 3   pairs, then stable.
```

`person × person` is finite, so the chain has finite height; it cannot climb forever and the loop
provably lands on the transitive closure `{(a,b),(b,c),(a,c)}`.

## 5. Decode a real fragment

The `APP` rule (discrete function application), Fig. 5, §4.1[^datafun]:

```
   ∆; Γ ⊢ e₁ : A → B      ∆; · ⊢ e₂ : A
  ───────────────────────────────────────  APP
          ∆; Γ ⊢ e₁ e₂ : B
```

Symbol-by-symbol:

| Symbol | Plain-English meaning |
|---|---|
| `∆; Γ ⊢ e₁ : A → B` | premise 1: `e₁` is a function from `A` to `B`, typed using discrete vars `∆` *and* monotone vars `Γ`. `e₁` itself may depend on the live monotone context. |
| `∆; · ⊢ e₂ : A` | premise 2: `e₂` types at `A` using discrete vars `∆` and an **empty** monotone context. `e₂` may use nothing from `Γ`; this is the "wipe." |
| `∆; Γ ⊢ e₁ e₂ : B` | conclusion: applying `e₁` to `e₂` yields `B`. Because the whole judgment's promise is "monotone in `Γ`," this application is monotone in `Γ` even though `e₁` itself need not be. |

Why the wipe is forced: `e₁ : A → B` is a *discrete* (possibly non-monotone) function; nothing
guarantees it respects any order on its argument. If `e₂` were allowed to read `Γ` (say,
`e₂ = x` for some monotone `x : A ∈ Γ`), then `e₁ e₂` could jump around non-monotonically as
`x` moves up the order, breaking the outer judgment's own promise. Forcing `e₂`'s monotone
context to `·` makes `e₂` a *constant* with respect to `Γ`, exactly a boxed value being fed to
an ordinary function, which is why the paper reads this as a hidden comonad's elimination form.
Contrast `APP⁺` (monotone application), same figure, which drops that restriction because both
`e₁ : A →⁺ B` and its argument are already promised monotone:

```
   ∆; Γ ⊢ e₁ : A →⁺ B      ∆; Γ ⊢ e₂ : A
  ─────────────────────────────────────────  APP⁺
             ∆; Γ ⊢ e₁ e₂ : B
```

Same conclusion shape, no wipe, because when the function itself is monotone, applying it to a
monotone argument stays monotone; the "constancy" firewall is only needed to contain a
non-monotone function.

## 6. Learning path

1. Davey & Priestley ch. 1-2[^davey]: posets, monotone maps, semilattices, Knaster-Tarski.
   Skim, don't master; you need recognition, not proofs.
2. Pierce, TAPL ch. 9[^tapl]: if `Γ ⊢ e : A` and inference-rule notation aren't already
   fluent, this is the single highest-leverage hour.
3. Pfenning & Davies §1-3[^pfenning-davies]: the dual-context (`∆; Γ`) judgmental style
   Datafun borrows wholesale; read this *before* Datafun §4, not after.
4. Milewski, "Functors" then "Natural Transformations" then "Adjunctions"[^milewski]: just enough
   to parse Fig. 7's `Set ⇄ Poset ⇄ SemiLat` and Fig. 9-10's denotations.
5. Datafun itself[^datafun]: read §1-4 straight through (skip §5-6, the formal metatheory), then
   circle back to §5 (denotational semantics) once §4's rules feel familiar.
